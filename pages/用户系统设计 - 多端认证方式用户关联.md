- 首先，系统 `user_id` 才是我们唯一认可的系统用户，其他认证方式都认为是一种绑定动作。
	- 包括：账号、手机号、邮箱、微信小程序用户。
- ## 登录注册策略
	- 有如下策略：
		- 每种认证方式，都询问用户，是否要绑定已有账号。
		  logseq.order-list-type:: number
			- 如果不绑定，就直接创建新用户并关联，
			  logseq.order-list-type:: number
			- 如果绑定。
			  logseq.order-list-type:: number
				- 如果实现选择了某种认证方式（比如：手机号）作为账号关联锚点，则让用户关联这种方式即可。
				  logseq.order-list-type:: number
				- 如果系统没有选择账号关联锚点，则用户可以选择任何认证方式进行关联。
				  logseq.order-list-type:: number
		- 选择某种认证方式（比如：手机号）作为账号关联锚点，认证通过后，直接创建系统用户并关联，避免所有认证方式都要询问绑定。
		  logseq.order-list-type:: number
	- ==感觉国内使用手机号作为账号关联锚点是比较合适的，否则在多平台都有登录的情况下，用户也会觉得很乱。==
- ## 关于账号关联锚点
	- 如果账号关联锚点认证后（比如手机号），可以直接创建系统用户（即注册）
		- 那么，意味着，系统用户只能关联 1 个这种认证方式（其他认证方式可以关联多个 id）。
		- 因为，认证通过后，不会询问用户是否要绑定已有账号。
		- 除非是用户在登录后，主动绑定，但这时，就可能面临账号合并问题。
	- 所以，可以这样：
		- 认证登录时，直接注册。
		  logseq.order-list-type:: number
		- 认证登录后，用户可以增加手机号绑定。
		  logseq.order-list-type:: number
		- ==但是，如果用户不小心直接注册了要用于绑定的手机号，那后续又涉及到了账号合并。==
- ## 强制用户使用账号关联锚点登录
	- 比如在微信小程序认证场景，我们希望删减：微信小程序认证后，还需要用户选择创建新用户还是绑定已有用户。
		- 一是避免用户错点了 “创建新用户” 。
		- 二也是简化流程。
	- ```
	  POST /auth/wechat/login (传入 loginCode)
	          │
	          ├─ openid 已绑定
	          │      └─ 返回正式 Token
	          │
	          └─ openid 未绑定
	                 └─ 返回 bindTicket
	                          │
	  POST /auth/wechat/phone-login (传入 phoneCode 和 bindTicket)
	                          │
	                          ├─ 手机号已存在 → 绑定微信并登录
	                          └─ 手机号不存在 → 创建用户、绑定两种身份并登录
	  ```
	- 注意，这里微信小程序用户绑定的仍然是系统用户，而非手机号，手机号也只是作为一种认证的方式。这里手机号只是为了帮助我们找到手机号所关联的系统用户。
- ## 关于修改绑定信息
	- 可以修改，没有问题，但是要使用准确的文字描述，避免用户误解修改的后果。
- ## 关于账号合并
	- 比较复杂，最好保证不会出现需要账号合并的场景。
	- 最好遵循如下策略：
		- 有一个账号没有产生业务数据，则直接新增绑定即可。
		  logseq.order-list-type:: number
		- 两边都有业务数据：
		  logseq.order-list-type:: number
			- 不提供通用自助合并（可以请求客服处理）。
			  logseq.order-list-type:: number
			- 提供特定数据的自助合并。
			  logseq.order-list-type:: number
