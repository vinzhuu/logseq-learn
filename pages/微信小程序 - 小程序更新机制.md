- ## 小程序代码包
	- 首先, 必须知道的一点是: **微信客户端** 启动 **小程序** 前, 必须先将 **小程序代码包** 下载到本地.
	- 也即, 打开 **小程序** 时, **微信客户端** 访问的是 **本地离线保存** 的 **小程序代码包** , 而非 **实时访问** 服务器上的 **小程序代码包** .
- ## 小程序更新步骤
	- 小程序更新可以分为如下几步:
		- **检查** : **微信客户端** 在恰当的时机, **检查** 本地已下载的小程序, 是否有新版本.
		  logseq.order-list-type:: number
		- **下载** : **微信客户端** 在恰当的时机, **下载** 新版本代码包.
		  logseq.order-list-type:: number
		- **使用** : **微信客户端** 在某次启动小程序时, **使用** 新版本代码包启动.
		  logseq.order-list-type:: number
- ## 涉及更新的流程
	- 小程序更新, 主要涉及如下流程, 它们互不影响 (或许会有协调机制, 保证它们在检查更新和下载新版本时, 不会冲突):
		- 后台定期版本 **检查** 流程 (**微信客户端** 定期执行, 与小程序是否启动无关).
		  logseq.order-list-type:: number
		- 同步更新流程 (发生在小程序启动前 ).
		  logseq.order-list-type:: number
		- 异步更新流程 (发生在小程序启动后 ).
		  logseq.order-list-type:: number
- ## 后台定期版本检查 流程
	- 定期 **检查** 本地已下载的小程序, 是否有新版本.
		- 如果有, 则将 **小程序** 标记为 **待更新** .
- ## 同步更新流程
	- ### 只涉及冷启动
		- 关于 **同步更新** , 在 [小程序运行时 - 更新机制](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/update-mechanism.html) 虽然没有强调是 **冷启动** , 但我们其实可以推测, 这里说的 **启动** 应该就是特指 **冷启动**
		- ( [[微信小程序 - 小程序生命周期]] 有提到: 一般讲 **启动** 就是说 **冷启动** )
	- ### 流程图

	- ### 同步阻塞
		- 上述流程, 各步骤是同步执行的, 会影响小程序的 **启动耗时** .
			- 特别是 **下载** 可能会比较耗时
	- ### 小程序最低可用版本
		- 在 [小程序管理页](https://mp.weixin.qq.com/) **设置 - 基本设置 - 小程序最低可用版本** 中设置.
		- 如果要启动的版本低于这个设置, 则无法启动.
			- 可以用于: **强制微信客户端更新小程序** .
	- ### 优先使用本地版本
		- 在 [小程序管理页](https://mp.weixin.qq.com/) **设置 - 基本设置 - 优先使用本地版本设置** 中设置.
		- 如果 **本地缓存版本** 不低于这个设置, 则优先使用 **本地缓存版本** , 不进行 **同步更新** .
			- [优先使用本地版本设置](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/update-mechanism.html#%E4%BC%98%E5%85%88%E4%BD%BF%E7%94%A8%E6%9C%AC%E5%9C%B0%E7%89%88%E6%9C%AC%E8%AE%BE%E7%BD%AE) 中有提到: `同时将会异步下载最新版本的代码包` .
				- 我理解为, 这里是在说下文的 **异步更新流程** , 而非在启动前又单独进行 **异步下载** .
	- ### 文档未明说的
		- 一次冷启动流程, 是否可能发生多次检查更新?
			- 如果小程序 **长时间未使用** , 则冷启动前会发生一次 **同步检查更新** , 冷启动后, 又会发生一次 **异步检查更新** .
			- 文档中未明说, 但 ChatGPT 讲, 微信客户端有自己的处理机制, 做到只检查一次.
		- 一次冷启动流程, 如果已经发生了 **同步更新** , 是否还会发生 **异步版本检查** ?
			- 文档中未明说, 不过从工程角度讲, 在 **同步更新** 后, 再进行 **异步版本检查** , 应该大部分时候都不会发现新版本.
- ## 异步更新流程
	- ### 异步
		- 此流程是在小程序启动之后 **异步开启** 的.
			- ==因此, 不会阻塞小程序启动. ==
	- ### 热启动与冷启动
		- 在 [UpdateManager](https://developers.weixin.qq.com/miniprogram/dev/api/base/update/UpdateManager.html) 的 `onCheckForUpdate` 有提到 **热启动** 也会发生版本检查.
		- 但是, 文档中没有明确说明, **热启动** 的 **异步版本检查** 会有什么动作.
			- ChatGPT 觉得可能只会 **检查更新, 并标记待更新** , 不会进行下载.
			- ==我觉得可能与 **冷启动** 的流程  一致==
	- ### 流程图
		- {{renderer :mermaid_6a26c39e-baad-4c6c-8ba2-87eb23950812, 3}}
			- ```mermaid
			  flowchart TD
			      %%  ====================================================
			      %%  ============ 预设
			      %%  ====================================================
			  
			      START([开始])
			      END([结束])
			  
			      %%  ====================================================
			      %%  ============ 用户确认重启
			      %%  ====================================================
			  
			      relaunchConfirm[提示用户重启小程序更新新版本] --> userClickConfirm{用户是否确认重启}
			      userClickConfirm -->|是| relaunch[用新版本重启小程序]
			      userClickConfirm -->|否| continueToUse[继续使用当前已启动的小程序版本]
			  
			      relaunch --> END
			      continueToUse --> END
			  
			      %%  ====================================================
			      %%  ============ 开始
			      %%  ====================================================
			  
			      START --> checkUpdate[检查新版本, 异步触发 UpdateManager.onCheckForUpdate]
			  
			      checkUpdate --> hasUpdate{是否有新版本}
			  
			      %%  ====================================================
			      %%  ============ 有新版本
			      %%  ====================================================
			  
			      hasUpdate -->|是| download[下载最新版本]
			  
			      %%  ============ 下载成功
			      download --> downloadSuccess{是否下载成功}
			      downloadSuccess -->|是, 异步触发 UpdateManager.onUpdateReady| markNextLaunchVer[将新下载的版本标记为下次冷启动版本（即 下次冷启动流程的 '缓存版本'）]  
			      markNextLaunchVer --> higherThanMin{当前版本是否 大于等于 '小程序最低可用版本'}
			  
			      higherThanMin -->|否| relaunchConfirm
			      higherThanMin -->|是| END
			  
			      %%  ============ 下载失败
			      downloadSuccess -->|否, 异步触发 UpdateManager.onUpdateFailed| END
			  
			      %%  ====================================================
			      %%  ============ 没有新版本
			      %%  ====================================================
			  
			      hasUpdate -->|否| END
			  ```
	- ### UpdateManager 的事件监听器
		- UpdateManager 的 `onCheckForUpdate` , `onUpdateReady` , `onUpdateFailed` 都是在接收到事件通知后异步执行的, 不会阻塞上述流程.
		- 具体内容参见下文的 `UpdateManager` 小节.
	- ### 下一次冷启动流程
		- [2. 启动时异步更新](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/update-mechanism.html#_2-%E5%90%AF%E5%8A%A8%E6%97%B6%E5%BC%82%E6%AD%A5%E6%9B%B4%E6%96%B0) 中有提到: `新版本的小程序需要等下一次冷启动才会使用` .
			- ==我理解为== : 此次下载的 **最新版本的代码包** , 被标记为了下次冷启动的版本, 即 **同步更新流程** 所说的 **缓存版本** .
			- 那么下一次 **冷启动** 的流程,  就和 **同步更新流程**  一致了.
- ## UpdateManager
	- ### UpdateManager 对象
		- UpdateManager 实例全局唯一, 用来管理小程序更新.
		- 可通过 [wx.getUpdateManager](https://developers.weixin.qq.com/miniprogram/dev/api/base/update/wx.getUpdateManager.html) 接口获取实例.
	- ### UpdateManager 对象的方法
		- ``` js
		  // ================ 客户端主动触发
		  
		  // 小程序每次启动（包括热启动）后, 异步自动检查更新后, 触发
		  // (可以获取自动检查更新的结果)
		  UpdateManager.onCheckForUpdate(function listener)
		  
		  // 下载小程序的新版本成功后 触发
		  // (可以在此处弹框提示用户可以使用新版本, 然后调用 applyUpdate() 强制使用新版本重启)
		  UpdateManager.onUpdateReady(function listener)
		  
		  // 下载小程序的新版本失败 (比如 网络原因) 后 触发 
		  UpdateManager.onUpdateFailed(function listener)
		  
		  // ================ 开发者主动调用
		  
		  // 强制小程序重启, 并使用新版本.
		  // 一般在小程序新版本下载完成后（即收到 onUpdateReady 回调）调用.
		  UpdateManager.applyUpdate()
		  ```
	- ### onCheckForUpdate
		- ==哪些情况会检查更新:==
			- 微信客户端的独立定时任务.
			  logseq.order-list-type:: number
			- 冷启动前, 发现小程序长时间未使用, 会同步检查更新
			  logseq.order-list-type:: number
			- 冷启动后, 会异步检查更新.
			  logseq.order-list-type:: number
			- 热启动后, 会异步检查更新.
			  logseq.order-list-type:: number
		- 他们底层应该走的都是同一个 `checkForUpdate` 逻辑.
		- 但是, 应该只有最后两个, 会触发 `UpdateManager` 的 `onCheckForUpdate` 事件.
			- 因为前两个发生在小程序启动前, `UpdateManager` 的事件都还未注册呢.
	- ### onUpdateReady 与 onUpdateFailed
		- ==哪些情况会发生下载:==
			- 冷启动前, 发现小程序长时间未使用, 同步检查发现新版本时.
			  logseq.order-list-type:: number
			- 冷启动后, 异步检查发现新版本时.
			  logseq.order-list-type:: number
			- 热启动后, 异步检查发现新版本时. ==不确定会不会发生下载==
			  logseq.order-list-type:: number
		- 他们底层应该走的都是同一个下载逻辑.
		- 但是, 应该只有最后两个, 会触发 `UpdateManager` 的 `onUpdateReady` /  `onUpdateFailed` 事件.
			- 因为第一个发生在小程序启动前, `UpdateManager` 的事件都还未注册呢.
	- ### 示例: 弹框提醒用户可以重启以使用新版本
		- 弹框提示用户进行重启.
		- ``` js
		  const updateManager = wx.getUpdateManager()
		  
		  updateManager.onCheckForUpdate(function (res) {
		    // 请求完新版本信息的回调
		    console.log(res.hasUpdate)
		  })
		  
		  updateManager.onUpdateReady(function () {
		    wx.showModal({
		      title: '更新提示',
		      content: '新版本已经准备好，是否重启应用？',
		      success(res) {
		        if (res.confirm) {
		          // 新的版本已经下载好，调用 applyUpdate 应用新版本并重启
		          updateManager.applyUpdate()
		        }
		      }
		    })
		  })
		  
		  updateManager.onUpdateFailed(function () {
		    // 新版本下载失败
		  })
		  ```
- ## 版本更新调试
	- **微信开发者工具** 上, 可以通过开启 **编译模式** 的 **下次编译模拟更新** 开关来调试.
	  logseq.order-list-type:: number
	- 小程序的 **开发版** / **体验版** , 没有 **版本** 概念 (只能使用最后覆盖的版本), 所以无法在 **开发版 / 体验版** 上, 测试版本更新.
	  logseq.order-list-type:: number
- ## 新版本覆盖
	- 开发者在后台发布新版本之后, 无法立刻影响到所有现网用户.
	- 正常情况下, 在全量发布 24 小时之后, 新版本可以覆盖 99% 以上的用户.
